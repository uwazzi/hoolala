- 2026-10-27 (WP2): Email sign-in through Resend's HTTP API in new `src/channels/email.ts` (a channel, like `telegram.ts`; sends the magic link only). Without `EMAIL_API_KEY` on localhost the link is printed to the dev console; nowhere else is an email or link logged.
- 2026-10-27 (WP2): Login tokens and session tokens are 32 random bytes; D1 and KV store only their SHA-256. Sessions last 30 days; `getSessionUser` reads KV first and falls back to D1 when KV hasn't caught up. A token is consumed by one conditional UPDATE, so a double click can't sign in twice. Rate limits in KV: 3 links per email per 15 min, 10 per IP per hour, keyed by hashes.
- 2026-10-27 (WP2): API addition `PATCH /api/me {firstName}` for "first name on first sign-in" (1 to 30 letters; no digits, links or handles). `GET /api/me` returns only id, first name and 18+. Email sign-in sets `is_adult = 1` because the 18+ box is required before a link is sent.
- 2026-10-27 (WP2): Contract change in `src/types.ts`: `D1Database.batch` (one transaction) for delete account, plus `MeResponse`. Delete account removes check-ins, signals and everything hanging off them, responses, quick replies, moments, friendships, stay-in-touch choices, blocks both ways, compass, points, workings, sessions, login tokens and the reports they filed; `interactions` stay for the Live number with `signal_id` cleared; places and facts they added stay without `added_by`; reports about them stay for review; the users row stays as an empty tombstone (`deleted_at` set) so counts keep a valid id. Signing in again with the same email starts a new account.
- 2026-10-27 (WP2): Every non-GET `/api/` request with an `Origin` header from another origin gets 403, ahead of SameSite=None in Telegram (WP21).
- 2026-10-27 (WP2): Known limit: `GET /auth/verify` is single use, so an email security scanner that opens links could use it up. If that shows up in the dry run, switch to a confirm page that POSTs. Tests run D1 on Node's built-in `node:sqlite` with every migration and foreign keys on (`tests/helpers/env.ts`).

- 2026-10-28 (security): Key handling written down in `docs/SECRETS.md`: keys only in Worker secrets, Actions secrets or the macOS keychain; never in chat, issues, URLs or `VITE_*`; one narrow key per environment with an expiry. Agents read keychain entries at the moment of use and never print them. `npm run check:secrets` scans tracked files in CI; GitHub secret scanning and push protection confirmed on. Full history (66 commits) scanned: no key found.
- 2026-10-28 (WP20): Cities are a fixed list (Lausanne, Geneva, Zurich, Bern, Basel; 12 km around each centre) and a place's city comes from its own coordinates by pure code, so search-within-your-city needs no geocoding service. Places outside these cities can still be found by location, not by search. The web app imports the list from `src/rules/checkin.ts` (data only) so there is one source.
- 2026-10-28 (WP20): Map provider OpenStreetMap (Overpass) by default; Google Places (New) behind `PLACES_PROVIDER=google` with the key in a header and field masks set. A picked map place is fetched again by id on the server and must be within 150 m; the client sends only ids and coordinates. Saved location: OSM's own coordinates (open data, ODbL, attributed in the list) or, for Google, the person's coordinates, since Google's must not be stored. Migration 0003 adds `places.osm_id` and unique indexes on both external ids. Out of radius logs reason `no_places_nearby` (the schema has no separate reason).
- 2026-10-28 (WP20): One active check-in per person: a new check-in ends the old one and expires that person's open signals there, in one batch. A place someone adds stays `new` with 10 points pending until someone else checks in, which sets `first_other_checkin_at` and `active` (WP25 counts the points). Place names are checked by code rules only for now (no homes, addresses, links, emails or phone numbers); SCREEN IT joins in WP23.
- 2026-10-28 (dev): wrangler 4 makes `wrangler dev` present the custom-domain route as the Worker's origin, so local sign-in links pointed at production and the dev-only link printing never fired. `npm run dev` now passes `--infer-origin-from-routes=false`.
- 2026-10-28 (priority): WP21 Telegram paused (work kept on local branch `wp21/telegram`: sign-in from launch data with tests, Mini App launch in `web/`) to make the web app work end to end with real people first: onboarding (sign in, first name, check in) and Signals here (WP22). Telegram is a launcher, a login and a doorbell for 3 opt-in notifications; it never carries conversation between people.
- 2026-10-28 (WP22): One read endpoint, `GET /api/here`, builds the HERE screen (own signals with requests, answered signals, up to 3 to discover); the web app polls it every 5 s while visible. Every item passes `canSee` and `canSeeNames`; no user ids reach the client. Block and report take a signal or response id and resolve the person on the server. Accept counts capacity inside the UPDATE so concurrent accepts can't overfill. A signal never outlives its poster's check-in. Report hides the item for everyone at once (signal cancelled, response withdrawn) and logs it as `open` for review.
- 2026-10-28 (WP22): Code screening (`src/rules/screening.ts`) runs on every topic and curious line now: length, links, emails, phones, handles, dating and sexual words, selling, abuse, crisis words (fixed help message with 143 and 144). SCREEN IT adds the model in WP23 and never overrules a refusal. Spots: a place's own list, else five defaults. WHEN: now, in 30 minutes, or a time up to 90 minutes ahead.
- 2026-10-28 (copy): Two example topics in `SIGNALS-HERE.md` break the 60-character limit ("Coffee break at 15:00. Small talk welcome, work talk tolerated." is 63, "Anyone else stuck on a pitch deck? Moral support at the big table." is 66). The limit stands; the examples need shortening before they appear in the demo or the README.
- 2026-10-28 (WP5): The meet QR is a link (`/meet?code=XXXXXX`) opened with the phone's own camera, not an in-app scanner: no camera permission (the Permissions-Policy keeps `camera=()`), no scanner library; the 6-character code (no 0/O/1/I/L) is the typed fallback. Codes are stored hashed and last 10 minutes. Only a signal's owner and an accepted responder can meet; two responders on the same signal never saw each other's names, so they can't. Outsiders always get the same `not_found` as a wrong code, whatever the code's state. STAY IN TOUCH lives at `POST /api/meet/:id/stay-in-touch` (the plan said `/api/stay-in-touch/:signalId`) because the person is identified by the confirmed meet, not by the signal; it answers `{ok:true}` whatever the other chose.
- 2026-10-28 (WP6): `GET /api/live` is public and cached 30 s: hellos (both-confirmed `here` interactions since 27 Oct), connection rate (distinct accepted signals that have a confirmed interaction / distinct accepted signals), check-ins that worked (ok / all attempts; the first-try metric needs per-session tracking and waits for WP9), facts confirmed this week, hellos per place listed by name, never ranked. SAMPLE places aren't excluded yet because they don't exist yet (WP9). QR encoder `uqr` added (no dependencies, about 5 KB gzipped).
- 2026-10-28 (WP20, revised): Real towns and villages instead of the fixed five-city list, which showed Lausanne to anyone outside those cities. When someone shares location, the server asks OpenStreetMap's Nominatim (live, zoom 14, point rounded to 5 decimals, identifying User-Agent, no key) which village or town the point is in; only the name comes back and nothing about the person is kept. Places store that name in `city` plus an accent- and case-free `city_key` that search compares (migration 0004, which also turns the old city ids into names). Search by name takes any town as free text, pre-filled from the phone. The five cities stay as the fallback when Nominatim is slow or down, and as suggestions in the town field. This supersedes the first WP20 entry about cities.
